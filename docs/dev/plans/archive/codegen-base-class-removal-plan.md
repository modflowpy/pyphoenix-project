## Goal

Generated component classes should carry no hand-written structure: no field
overrides, no `__attrs_post_init__` logic, no special-cased base classes. Pure
behavior (factories, conversions) may stay on the classes as methods, but comes
from method-only mixins declared in codegen config, not from base classes that
codegen picks by name.

## Current state

- `flopy4/mf6/tdis_base.py` (`TdisBase`), chosen by codegen's `_base_class()` for `sim-tdis`. It:
  1. fills default `perioddata` (`nper` rows of `(1.0, 1, 1.0)`)
  2. derives `nper` from the row count, raising if an explicit `nper` other than 1 disagrees
  3. converts a `datetime` `start_date_time` to an ISO string
  4. exposes read-only `perlen` / `nstp` / `tsmult` column properties
  5. provides `get_dims`, `to_time`, `from_time`, `to_xarray` and `from_timestamps`
- `flopy4/mf6/utl/ncf_base.py` (`NcfBase`) overrides `wkt` / `crs_wkt` field
  types. `utl-ncf` is still in the codegen skip list. The concrete
  `flopy4/mf6/utl/ncf.py` is hand-written and adds `Ncf.from_grid()`.

## Findings

- **The NCF override is obsolete.** Codegen on the dev3 schema already emits
  `wkt: Optional[str]` and `crs_wkt: Optional[str]`, verified by generating
  `utl-ncf` into a scratch dir. Apart from `from_grid()`, the generated module
  matches the hand-written one. It adds `longname`s and uses `FloatArrayLike`
  instead of `NDArray` for latitude and longitude.
- **Nothing in the library needs the `perlen` / `nstp` / `tsmult` properties.** Their only readers are
  `to_time()`, `to_xarray()` and tests (`test_mf6_component.py:511-513`,
  `test_tdis_round_trip`, `test_tdis_period_columns_are_views`). Callers who
  want arrays can use `to_time()`. Keeping the properties keeps the array API
  on the class, which the refactor set out to remove.
- **Methods don't require base classes.** An instance method gets `self` and a
  classmethod gets `cls`, so the module that implements them never imports the
  generated class. There is no circular import.

## Design: method-only mixins from codegen config

Replace the name-based `_base_class()` special cases with a config table in
codegen:

```python
# flopy4/mf6/utils/codegen/make.py (or a config module)
_MIXINS = {
    "sim-tdis": ["flopy4.mf6.tdis_methods:TdisMethods"],
    "utl-ncf": ["flopy4.mf6.utl.ncf_methods:NcfMethods"],
}
```

The template emits `class Tdis(TdisMethods, Package):` plus the imports. Rules for mixins:

- methods only: no attrs fields, no `__attrs_post_init__`, no field overrides
- never redeclare fields. Annotate `self` / `cls` with the generated class,
  imported under `TYPE_CHECKING`:

  ```python
  if TYPE_CHECKING:
      from flopy4.mf6.tdis import Tdis

  class TdisMethods:
      def to_time(self: "Tdis") -> Time: ...

      @classmethod
      def from_time(cls: type["Tdis"], time: Time) -> "Tdis": ...
  ```

  The DFN stays the only source of field names and types. (`TdisBase`
  redeclared `time_units`, `start_date_time`, `nper` and `perioddata` under
  `TYPE_CHECKING`, a second copy that could drift silently.)

  mypy flags the annotation itself; see departure 1.

### Where DFN knowledge lives

- **MF6 input semantics** (field types, defaults, list-block dimensions) come
  from the DFNs only, through codegen features (see TDIS item 3). Mixins must
  not restate any of it.
- **flopy API conveniences** (`from_grid`, `to_time`, ...) convert to and from
  flopy types (`Grid`, `Time`) that MF6 knows nothing about, so they don't
  belong in the DFNs. `_MIXINS` records only "this component also gets these
  flopy methods". That knowledge belongs to flopy, and keeping it in one table
  is better than the name checks scattered through `_base_class()` today.
- Conversion methods **use** DFN-derived field names; that coupling is the
  point of a conversion. What's ruled out is **restating** those names or
  types anywhere else.

### Drift checks

- Codegen fails if a `_MIXINS` key matches no loaded DFN.
- mypy runs over the mixins using the annotated `self`, so a DFN field rename
  that breaks a mixin fails in CI.
- Round-trip tests (`Tdis` ↔ `Time`, `Ncf.from_grid`) cover runtime behavior.

Alternatives considered:
- **Bind free functions in the generated class body**
  (`from_grid = classmethod(ncf_from_grid)`). Works, but type checkers and IDEs
  handle `classmethod(<function>)` poorly.
- **Attach methods after import** (`Ncf.from_grid = ...` in an `__init__`).
  Hidden and invisible to type checkers. Rejected.
- **Find mixins by convention** (e.g. use `NcfMethods` automatically if
  `utl/ncf_methods.py` defines it). Removes component names from codegen, but
  a file's presence would silently change the generated class. Rejected in
  favor of the explicit table plus drift checks.
- **Generic name-matching converter for TDIS** (`Time` and the DFN share
  `nper`, `perlen`, `nstp`, `tsmult`, `time_units`, `start_date_time`). It
  relies on a naming coincidence, only TDIS benefits, and NCF has no such
  correspondence. Rejected.

The `Solution` base class could move into the same mechanism later. It is a
real base class, though, with behavior of its own, so that can wait.

## Departures and follow-ups

Where the implementation differs from the plan, and what is still open.

### 1. mypy flags `self: "Tdis"` on a mixin

The plan assumed mypy accepts a self type that is a subclass of the
enclosing class. It doesn't: it reports `The erased type of self "Tdis" is
not a supertype of its class "TdisMethods" [misc]` on each such signature.
It accepts only supertypes of the class, or a Protocol.

What was done: one `# type: ignore[misc]` on each mixin method's `def` line
(5 in `TdisMethods`, 1 in `NcfMethods`). The ignore covers only that
diagnostic on the signature:

- Method bodies are still checked against the generated class. Renaming
  `self.nper` to `self.nperx` fails with `"Tdis" has no attribute "nperx"`.
- Callers are typed correctly. `Tdis.from_time(...)` is revealed as `Tdis`,
  `Ncf.from_grid` has its full signature, and `Tdis.from_time(1)` is
  rejected.
- `cls(...)` keyword arguments are checked against the attrs `__init__`.

#### Mixin vs Protocol

Tested with mypy (scratch module, attrs classes):

| | mixin, `self: "Tdis"` (current) | mixin, Protocol `self` |
|---|---|---|
| diagnostic on the declaration | `[misc]` on each `def`, ignored | none |
| fields restated | no | yes: every field the mixins use, with types |
| drift in a mixin body (field renamed) | error in the mixin body | error only at call sites, as `Invalid self argument "Tdis" ...`; missed if no checked code calls the method |
| one mixin method calling another (`to_xarray` → `self.to_time()`) | works | error (`"_Fields" has no attribute "to_time"`) unless the method is also declared on the Protocol |
| factory `cls(...)` (`from_time`, `from_timestamps`, `from_grid`) | keyword arguments checked against the attrs `__init__` | error: a Protocol has no `__init__` (`Unexpected keyword argument "nper" for "_Fields"`). Needs an ignore, or `__init__` restated on the Protocol |
| caller-side types (`Tdis.from_time(...)` → `Tdis`) | correct | correct with `cls: type[T]`, `T` bound to the Protocol |
| IDE completion on `self.` in the mixin | from the real class | from the Protocol |

Callers get correct type hints either way. The Protocol removes the six
`[misc]` ignores, but needs a hand-maintained field list, needs ignores on
the three factories anyway, and weakens drift detection. **Recommendation:
keep the mixin + `self: "Tdis"`.**

If the ignores need to go, have **codegen emit the Protocol** (`TdisFields`
in `tdis.py`, from the same DFN fields) and import it into the mixin under
`TYPE_CHECKING`. That removes the hand-maintained field list, but the
factory and method-to-method problems above remain.

Other alternatives, not taken:
- `class TdisMethods(Tdis if TYPE_CHECKING else object)`. This is circular,
  because `tdis.py` imports the mixin.
- Turning off `misc` for the mixin modules in the mypy config. That is
  broader than needed.

Open: pyright/basedpyright (not installed in the dev environment) may treat
`self: "Tdis"` differently. If IDE users run Pylance, check it and add
pyright-specific ignores if needed.

### 2. Row-count dimension: when explicit values are validated

TDIS item 3 is implemented as a general `Package` feature rather than
TDIS-specific setup:

- Codegen already worked out which DIMENSIONS field counts each list
  block's rows (`_build_block_property_specs`; `perioddata` → `nper`
  because it is the only field in the dimensions block). It used to emit
  only `auto_from=<block>`, a flag that nothing read. It now emits
  `dim="<dimension>"`. `Package._init_item_lists` also used to set
  `n<block>s`, a naming guess that matched no real field. That is removed.
- A dimension resolved for more than one block (MAW's `nmawwells` for
  packagedata, connectiondata and angledata; SFR's `nreaches`) doesn't
  count any one block's rows, so it gets no `dim`.
- 11 generated packages get a link now: TDIS, BUY, CSUB, LAK (×3), MVR,
  VSC, PRT-OC, PRP (×2), ATS, LAKTAB and SFRTAB. For all of them except
  TDIS this is new behavior: constructing with rows fills in the dimension
  (e.g. `nlakes`).

`Package._set_dim_from_rows(dim, nrows)`:

| dimension value                    | result                     |
|------------------------------------|----------------------------|
| `None`, `0` or the field's default | set to `nrows`             |
| explicit and `< nrows`             | `ValueError`               |
| explicit and `>= nrows`            | kept, no error             |

`TdisBase` raised on any mismatch. Now `Tdis(nper=3, perioddata=[one
row])` is accepted silently and writes `NPER 3` with one PERIODDATA row,
which MF6 rejects at run time. Too few rows can't be an error in general:
some linked dimensions are upper bounds, where fewer rows is valid input
(ATS `maxats`: the Fortran read loop stops at END). The dev3 schema doesn't
say which kind a dimension is: `dfnspec.md` says a list's `shape` "names a
declared dimension that bounds the list", and neither `List` nor `InputDim`
records whether that bound is exact. The name doesn't say either: MVR
`maxpackages` is exact despite the `max` prefix (`gwf-mvr.f90` errors if
`npak /= maxpackages`).

Other rough edges:
- The TDIS `nper` default is `1`, so an explicit `nper=1` can't be told
  apart from the default. `Tdis(nper=1, perioddata=[3 rows])` becomes
  `nper=3` without an error. `TdisBase` behaved the same way.
- The dimension is synced only at construction. Adding rows later doesn't
  update it (same as before).

Plan: **`../modflow-devtools/list-shape-bounds-plan.md`**. In short:
- The legacy `.dfn` format already marks upper bounds with a `<` prefix
  (`shape (<nstp)` on OC `steps`, `(<time_series_name)` on `utl-ts`), and
  an unmarked dimension is exact. Both devtools migrations drop the marker
  (`_parse_shape`). Plan: keep it in dev3 (`shape: ["<maxbound"]`), mark
  the upper bounds that lack it (all `maxbound` period lists, ATS
  `maxats`, probably HFB `maxhfb` and CSUB `maxsig0`), and treat unmarked
  shapes as exact.
- Fix the missing shapes: TDIS perioddata → `[nper]`, ATS perioddata →
  `[<maxats]`. Upstream, add `shape (nper)` / `shape (<maxats)` to the
  modflow6 `.dfn` files.

flopy4 follow-up once that lands:
- Link list dimensions only through an explicit `shape`, and drop the
  single-dimension fallback in `filters.list_col_dim`.
- Parse the `<` prefix into field metadata. `_set_dim_from_rows` raises on
  any mismatch for exact dimensions, and only on too many rows for `<`
  bounds.

Rejected: inferring the kind from the name (`max*` means upper bound). MVR
shows it's wrong.

### 3. Default rows

The DFN `default_value` for list blocks is now emitted as `default_rows=`
metadata; only TDIS has one: `((1.0, 1, 1.0),)`. The field default itself
stays `None`. `Package` fills the rows at construction and repeats a
one-row default `dim` times, so `Tdis(nper=3)` gets three rows. Treating a
one-row default as a per-row default is an interpretation; the DFN doesn't
say so. Open: confirm with the MF6 DFN maintainers, or make it explicit in
the schema.

### 4. No default `Package.get_dims`

Dropped from TDIS item 3. A default `get_dims` makes every package a
`DimensionProvider`. `DimensionResolverMixin._get_all_dimensions` raises
when two children provide the same dimension name, and names like `ncpl`
(DIS and NCF) and `maxbound` repeat across packages. `get_dims` stays a
`TdisMethods` method. Open: whether dimension resolution should be scoped
(e.g. only DIMENSIONS fields that other components consume) so that a
generic implementation becomes possible.

### 5. `Time` conversions stay in `TdisMethods`

TDIS item 2 planned to move them to `utils/time.py` with thin wrappers on
`Tdis`. The mixin is already the single home for them, and moving them
would add code. Not done.

### 6. `to_time()` was broken on develop

It passed `nper=` and `start_date_time=`, which `ModelTime` doesn't accept,
and nothing called it in the tests. Fixed (`start_datetime=`, no `nper`).
`test_tdis_from_timestamps` now round-trips `Tdis.from_time(tdis.to_time())`.
`to_xarray()` goes through `to_time()`.

### 7. `start_date_time` datetime conversion

The conversion is removed from construction. `from_time()` converts to ISO
text, and the field accepts `str` only. A datetime DFN type (#378) remains
the proper fix.

### 8. Generated griddata fields don't emit `layered`

**Done** (on this branch, not yet staged). Implemented differently from
step 1 below: `filters.field_metadata` emits `layered=True` only when the
DFN says so, and an absent key means False everywhere. Ingress and egress
already read it with a False default; `netcdf.py` `_ArrayInfo` was the
only reader defaulting to True, and it now defaults to False. Every
netcdf field with an `ncpl` shape already set `layered=False` explicitly,
so that change has no effect on current classes. Regeneration added
`layered=True` to griddata in 12 modules (NPF, STO, IC, CSUB, DSP, MST,
IST, CND, EST, MIP). Side effect: egress now writes those arrays in
`LAYERED` form when the model has `nlay > 1`, as it already does for DIS
`botm`. The other `layered` hits in `netcdf.py` (around lines 425, 567 and
597) concern the model's mesh type, not field metadata. Test:
`test_layered_griddata_metadata`. Smoke passes (1407 passed).

Original plan:

The generated `Ncf.latitude`/`longitude` lost the hand-written
`layered=False`. The DFN and the devtools migration are correct: dev3
reports `layered: False` for `utl-ncf` latitude and `layered: True` for
`gwf-npf` k. The gap is in flopy4:

- Codegen emits `layered` only for period `readarray` fields
  (`make.py`, `_ra_meta["layered"]`). Static griddata fields get none;
  generated `npf.py`'s `k` has no `layered` either.
- `netcdf.py` (`_ArrayInfo`) reads `f.metadata.get("layered", True)`, so a
  missing value means layered. That happens to be right for NPF `k` and
  wrong for NCF `latitude`/`longitude`. For non-layered fields it controls
  whether `ncpl` is normalized to `nodes`.
- The tests pass because NCF latitude/longitude have `netcdf: False` and
  never reach that code path.

No devtools change is needed. Fix, in flopy4:
1. Codegen (`make.py`): emit `layered=<Array.layered>` in the field call
   for every `Array` field, griddata included, not only period
   `readarray` fields.
2. `netcdf.py` `_ArrayInfo`: change `f.metadata.get("layered", True)` to
   `False`, or require the key. Check the other `"layered"` reads in
   `netcdf.py` (around lines 425, 567 and 597), and any in `spec.py`,
   adapters or the codec, for the same default.
3. Hand-written DIS/DISV fields already set `layered=` explicitly; no
   change.
4. Regenerate (`dfn2py --existing-only`) and check the diff: `layered=True`
   on NPF/STO/IC-style griddata, and `layered=False` on NCF
   latitude/longitude and similar.
5. Test: a NetCDF export of a layered griddata field (NPF `k`) still gives
   the `nodes` / per-layer layout, and `Ncf.latitude`'s `_ArrayInfo` keeps
   its `ncpl` shape.

### 9. Line count

Component-specific hand-written code went from 206 lines to 123 (removed
`tdis_base.py`, `ncf_base.py` and the hand-written `ncf.py`; added
`tdis_methods.py` and `ncf_methods.py`). Shared codegen/`Package`/`spec`
