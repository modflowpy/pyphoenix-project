# FloPy 4 software design description (SDD)

This is the Software Design Description (SDD) document for FloPy 4, also called *the product*.

This document describes a tentative design, focusing on "core" functional requirements. Some attention may be given to architecture, but non-functional requirements are largely out of scope here.

## Conceptual model

This document follows MODFLOW 6 terminology where applicable, with modifications/translations where appropriate.

Core concepts include:

- **specification**: defines the complete MODFLOW 6 input format
- **definition**: defines input format for a single MF6 component
- **component**: an element of a simulation, e.g. a model/package
- **variable**: an input variable, e.g. data or configuration
- **block**: a named collection of input variables

A set of definition files make a specification. A definition file specifies exactly one component. Components may have zero or more variables (some exchanges, for instance, have none).

## Object model

The object model is an object-oriented interface to MODFLOW 6 (FUNC-4). For every MF6 component module the product will generally have a corresponding class.

Component classes function simultaneously as **data** and **specification**. It should be straightforward to read the component specification off the class definition, and to inspect it programmatically (FUNC-21). Likewise it should be easy to retrieve a variable's value from an instance of a component (FUNC-4).

### `attrs`

There are many ways to implement an object model in Python. Dictionaries, named tuples, plain classes, `dataclasses`...

`dataclasses` are derived from an older project called [`attrs`](https://www.attrs.org/en/stable/) which has some [extra powers](https://threeofwands.com/why-i-use-attrs-instead-of-pydantic/).

Our first proof of concept demonstrated a nested hierarchy of classes forming a component tree. We propose to use `attrs` for a similar hierarchy, providing both spec and data access.

### `xarray`

XArray provides abstractions for working with related datasets in a hierarchical context, some of which may share the same spatial/temporal indices and/or coordinate systems. 

We propose to follow [imod-python](https://github.com/Deltares/imod-python) in adopting [xarray](https://docs.xarray.dev/en/stable/index.html) as our components' onboard data store, e.g. in a `.data` attribute.

For nodes in the context tree (i.e., components with children), `.data` will be a [`DataTree`](https://docs.xarray.dev/en/stable/generated/xarray.DataTree.html). For leaves in the tree, `.data` will be a `Dataset`.

### `attrs` + `xarray`

Combining these patterns naively would result in data duplication and synchronization challenges.

We can arrange instead for `attrs` attribute access to proxy the xarray store via `__getattribute__`.

Likewise, we can use [`on_setattr`](https://www.attrs.org/en/stable/api.html#core) to intercept values sent to the `attrs` attributes and send them to the xarray store.

We must also intercept arguments passed to the initializer and send them to the xarray store instead of the appropriate `attrs` attribute. As a consequence, we cannot rely on `__init__()` methods generated by `attrs`.

However, other `attrs` functionality should "just work" (e.g. validation, `__repr__`/`__eq__`/etc), due to the operation of `__getattribute__` under the hood.

This concept can be packaged in a class decorator, which can be applied directly to component classes.

The `__init__()` method should not be burdensome to generate via Jinja &mdash; it can merely send all arguments to a generic function which sets corresponding entries in the component's `.data` attribute.

## Data types

MODFLOW 6 defines a [type system for input variables](https://github.com/MODFLOW-USGS/modflow6/tree/develop/doc/mf6io/mf6ivar#variable-types). We adapt this mostly unmodified.

A variable is either a scalar or a composite.

Scalars include integer, double precision, boolean, string, and path types.

Composites include array, list, product (record), and sum (union) types.

Translating from MF6:

- A "keystring" is a union of records. 
- A "recarray" is a list. 

MF6 places some constraints on composite variables. These are explained below.

### Records

A record is an ordered, named set of scalars.

For MF6, a record is a whitespace-delimited line of text. While in principle a record's fields are named, MF6 may or may not expect particular values to be "tagged" (as indicated in definition files).

### Unions

A union's choice types must be records. Unions may not contain scalars directly.

### Arrays

An array is an N-dimensional array of homogeneous (scalar) type.

We can accept any `numpy.typing.ArrayLike` value, whether a standard `ndarray` or some other flavor (i.e. "duck arrays").

A common case will be lazy (e.g. dask) arrays for larger-than-memory operations.

We can [implement custom array-likes](https://numpy.org/doc/stable/user/basics.interoperability.html) if there is a good case for it.

Arrays can be type hinted in full detail in component classes, e.g. `NDArray[np.floating]`, while methods can generally have more lenient type hints (e.g. `ArrayLike`) and perform any necessary type checks at runtime.

### Lists

A list's item type may be a record or union of records. Like unions, lists may not contain raw scalars. We consider a collection of scalars an array.

A list of records is regular, i.e. tabular. A list of unions can be irregular (i.e. rows may have different element counts).

Regular lists are representable with Python builtin collections as well as tabular data structures, e.g. `pd.DataFrame` or `np.recarray`. Avoid columns of dtype `np.object_` &mdash; e.g. prefer store grid cell indices as separate columns `i`, `j`, `k`, not a single column.

Irregular lists are not "tabular".

For instance:

- A `packagedata` block is typically a list of records of a single type (thus regular/tabular).
- A `period` block is typically a list of unions, where each item may be a different record type (thus irregular).
