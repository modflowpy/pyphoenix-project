# Record/Item consolidation plan

## Background

`flopy4/mf6/row.py` (`Row`) and `flopy4/mf6/record.py` (`Record`) are two
independent attrs mixins generated by the codegen pipeline:

- `Record` — one compound value with a leading trigger keyword (an inner
  options-block record, e.g. `Concentrationprint`). Single occurrence.
- `Row` — one row of a repeating tabular block (`packagedata`,
  `connectiondata`, period data). Many occurrences, list/dict-valued field.

Both are attrs mixins providing symmetric `to_*`/`from_*` token
(de)serialization, introspecting the concrete class's own `attrs.fields()` as
the schema (no separate Schema/Column description). `Record` subclasses drop
the "Record" suffix in generated names (`Concentrationprint`, not
`ConcentrationprintRecord`); `Row` subclasses currently keep the "Row" suffix
(`PackagedataRow`, `ConnectiondataRow`) — this asymmetry, plus a suspicion
that the two classes are redundant, is what prompted this review.

## What the review found

Tracing `to_row`/`from_row` against `to_tokens`/`from_tokens` line by line
turned up several differences that looked structural at first but are
actually artifacts of what the current MF6-devtools DFN corpus happens to
contain, not properties of "single value" vs "list item":

1. **Tagged-field handling.** `Row`'s tagged branch only ever emits a bare
   flag token (`if val: row.append(f.name.upper())`) and would silently drop
   the value for a `NAME value`-style tagged field. This is because every
   `tagged=True` Row column today comes from `role == "inline_keyword"`,
   which is always a presence-flag keyword — never exercised with a real
   value. `Record`'s tagged branch already handles both cases correctly.
   Not a deliberate protocol difference — an unexercised code path.

2. **Union dispatch.** `dispatch_union_row`/`parse_union_rows` (choose which
   of several sibling classes a raw token blob belongs to, by leading
   keyword) is implemented only for `Row`. But `can_generate_record_class`'s
   own docstring already flags "Records with unsupported child types (list,
   union) fall back to TODO comments" as a known gap — i.e., a standalone
   `Record` field that's a keyword-discriminated union of several `Record`
   shapes is an anticipated case, just not one the current corpus exercises.
   Dispatch-by-keyword isn't inherently a list concept.

3. **Positional vs. self-describing parsing.** `Row.from_row` infers how
   many optional, non-tagged trailing columns are present from a token-count
   "budget" (needed because MF6 sometimes writes a whole group of untagged
   optional columns together or not at all, gated by an unrelated flag —
   e.g. EVT's `pxdp/petm/petm0`). `Record.from_tokens` never needs this
   because every `Record` in the corpus happens to be fully
   keyword-tagged. Nothing about being a standalone field prevents the same
   ambiguity from occurring there too.

4. **External parse context.** `ncelldim` is inferred from the row data
   itself (`infer_ncelldim` — no external state). `naux`/`boundnames` are
   real package-level facts (from the `AUXILIARY`/`BOUNDNAMES` options)
   threaded explicitly through `Row.from_row`'s signature and the
   `row.py` helpers. Real hardcoding, but a closed, stable set of two names
   — not worth generalizing to an open context bag right now.

What's left as a genuine, irreducible difference — concepts that only make
sense for one member of a collection of same-shaped things, never for a
solitary value — is narrow:

- `cellid` (composite spatial index packing/unpacking)
- `index`/`pk`/`fk` (0-based↔1-based row numbering, cross-row references)
- `aux`/`boundname` (per-entry trailing decoration — "which one am I")

## Target design

Two classes, one inheriting the other:

- **`Record`** (`flopy4/mf6/record.py`, unchanged module) — the base.
  Carries `_keyword`/`_extra_tokens`, unified tagged/untagged field
  emission (bare-flag *and* `NAME value` forms), and the generalized
  optional-column budget inference for untagged trailing fields (reserving
  zero slots by default, since plain records have no aux/boundname to
  reserve for). Generalized union dispatch (`dispatch_union`/parse-by-keyword
  helper) also lives here, since arms don't need to be list items — they
  just need to share the `_keyword` convention.

- **`Item(Record)`** (`flopy4/mf6/item.py`, renamed from `row.py`) — adds
  everything that's actually about being one entry in a collection:
  `index`/`pk`/`fk`/`cellid` field metadata, `aux`/`boundname` trailing
  columns, and the `ncelldim`/`naux`/`boundnames` context params on
  `from_tokens`. Plain `Record.from_tokens` keeps its current simple
  signature (no context params) — only `Item` needs them.
  `to_row`/`from_row` are renamed to override `to_tokens`/`from_tokens`
  (one verb pair across both classes).

  The plural, list-level orchestration helpers (`infer_ncelldim`,
  `construct_row`, `parse_union_rows`, `normalize_aux_keys`,
  `row_list_type`) move into `item.py` as module functions operating on
  `Item` subclasses — they're about handling *many* rows at once, not a
  property of one item.

### Naming changes (generated code)

- Drop the `Row` suffix from generated block-item classes to match how
  `Record` subclasses already work: `PackagedataRow` → `Packagedata`,
  `ConnectiondataRow` → `Connectiondata`, `TablesRow` → `Tables`,
  `VerticesRow` → `Vertices`, etc. Module-level aliases follow suit
  (`LakPackagedataRow` → `LakPackagedata`).
- The period-block item class is currently hardcoded to the literal name
  `"Row"` (`filters.py` `row_class()`, `package.py.jinja`), with a
  `_Row = Row` alias purely to dodge a mypy self-reference issue
  (`class Row(Row):` doesn't resolve). The public field is actually named
  `stress_period_data` (`make.py:956`, aliased from `_stress_period_data`),
  so derive the class name from that instead (`StressPeriodData`), the same
  way block-schema names are derived from `block_name`. This needs a real
  snake_case→PascalCase conversion (not bare `str.capitalize()`, which only
  works for the current single-word block names). Once the class isn't
  literally named `Row`/`Item`, the mypy-shadow alias hack is no longer
  needed and can be deleted.
- `flopy4/mf6/row.py` → `flopy4/mf6/item.py`; class `Row` → `Item`.
- `isinstance(x, Row)` checks in `unstructure.py`/`package.py` become
  `isinstance(x, Item)` — same behavior, since only true list members are
  ever `Item` instances (plain `Record` instances are not).

## Staged rollout

1. **Base classes.** Rewrite `record.py` (add unified tagged-field handling,
   generalized budget inference, generalized union dispatch) and
   `row.py` → `item.py` (`Item(Record)`, list-specific metadata/context,
   renamed `to_tokens`/`from_tokens`, moved orchestration helpers). No
   codegen changes yet. Sanity-check the new classes directly (construct a
   few instances by hand matching real generated shapes from `lak.py`,
   `oc.py`, `evt.py` to confirm round-trip behavior) before touching
   generation.

2. **Codegen.** Update `filters.py` (`row_class()` naming — drop `Row`
   suffix, proper PascalCase for `stress_period_data`; base-class references
   `Row`→`Item`), `make.py` (period/block class-name derivation, import
   selection), and `package.py.jinja` (drop the `_Row` alias block, update
   base-class references and the final alias loop). Update
   `test_mf6_codegen.py` expectations (it currently asserts literal
   `PackagedataRow`/`class ... (Row):` strings — grepped and confirmed these
   need updating, e.g. lines 259-347, 475).

3. **Verify on representative packages.** Regenerate just enough to check by
   hand — `gwf/lak.py` (static blocks + period keystring-union — exercises
   `Packagedata`/`Connectiondata`/`Tables`/`Outlets`/period `Item`) and
   `gwt/oc.py` (inner `Record` classes) — via
   `flopy4 mf6 sync MODFLOW-ORG/modflow6@develop --no-install --verbose`
   (the `generate-classes` pixi task). Diff against current output, confirm
   shapes match expectations, run `test_mf6_component.py` /
   `test_mf6_integration.py` against these two packages.

4. **Full regeneration.** Run the same sync across all packages
   (`generate-classes-preview` if new packages should also be picked up),
   run the full test suite, fix fallout package-by-package.

5. **Cleanup sweep.** Grep for any remaining references to the old names
   (`flopy4.mf6.row`, bare `Row` imports/usages, `*Row` class names) across
   `flopy4/`, `test/`, and docs/docstrings (e.g. `spec.py:184` docstring
   mentions `Row` in the `prefix=` explanation) to make sure nothing was
   missed.

## Open risks

- `test/mf6/test_mf6_row_api.py` was already deleted in a prior commit
  (1e56bae); no dedicated Row/Record unit test currently exists, so
  correctness will be verified through `test_mf6_codegen.py`,
  `test_mf6_component.py`, and `test_mf6_integration.py`. Worth considering
  a small dedicated `test_mf6_item_record.py` once the new classes land,
  covering the tagged-value fix and generalized union dispatch specifically
  (neither has a current test since neither is exercised by the existing
  corpus).
- Any hand-written code outside the generated files that imports
  `flopy4.mf6.row` or references `*Row` class names directly needs to be
  caught by the cleanup grep in stage 5.
